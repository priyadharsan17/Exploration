PySide6 + QML
Developer Guidelines

The mental model, architecture patterns, and practical rules for building clean, maintainable PySide6 applications with QML frontends. Read this before writing your first line.

1 The Mental Model

The single most important thing to internalise: QML owns the screen, Python owns the data and logic. They are two separate worlds connected by a thin, well-defined bridge. Never let either side reach across and mutate the other's internals directly.

┌─────────────────────────── QML / UI World ───────────────────────────┐ │ │ │ Window → Pages → Panels → Components → Delegates │ │ (declarative, property bindings, animations, user interaction) │ │ │ └──────────────────────┬────────────────┬──────────────────────────────┘ │ │ Signals ↑ │ │ ↓ Slots / Q_INVOKABLE (push data) │ │ (QML calls Python fn) │ │ ┌──────────────────────┴────────────────┴──────────────────────────────┐ │ │ │ QObject subclasses · QAbstractModels · @Property · @Slot │ │ (business logic, data, file I/O, network, computation) │ │ │ └─────────────────────────── Python / Logic World ─────────────────────┘

The three rules of the bridge

  1. Python → QML: emit a Signal. QML listens via Connections or property bindings.
  2. QML → Python: call a @Slot (or Q_INVOKABLE). Python executes and optionally emits a signal back.
  3. Shared state: expose it as a @Property(notify=signal). QML binds to it; Python updates the value and emits the notify signal; QML re-evaluates automatically.
💡
Think of Python as the server, QML as the client.

The client renders and accepts user input. The server owns truth. Communication happens over a typed API of signals, slots, and bindable properties — not direct memory access.

2 Application Architecture

Every PySide6 + QML application follows this four-layer structure. Keep the layers clean — resist the temptation to skip one.

LayerResponsibilityFiles
Entry Point Create QGuiApplication, instantiate models/backends, call setContextProperty, load the root QML file. main.py
Backend / Model All Python logic, data storage, computation. Subclass QObject or a model base class. No imports from QML. *_backend.py, *_model.py
Root QML Top-level ApplicationWindow or Window. Sets up the bridge: Connections, top-level layout, navigation host. MainWindow.qml
QML Components Reusable UI pieces. Communicate only through required property, explicit signal, and public methods. Never reach for global context properties. components/*.qml
main.py — canonical entry point 
import sys
from PySide6.QtGui import QGuiApplication
from PySide6.QtQml import QQmlApplicationEngine
from backend import MyBackend

app = QGuiApplication(sys.argv)

engine = QQmlApplicationEngine()
backend = MyBackend()                        # create BEFORE loading QML

engine.rootContext().setContextProperty(
    "backend", backend                        # expose as "backend" in QML
)

engine.load("MainWindow.qml")
if not engine.rootObjects():
    sys.exit(-1)

sys.exit(app.exec())
⚠️
Always create backend objects before loading QML.

If QML loads first it may try to resolve context properties that don't exist yet, leading to silent binding failures or undefined references.

3 Exposing Python Objects to QML

There are two complementary mechanisms. Use context properties for global singletons (backend, models). Use registered types only when you need to instantiate the object in QML itself.

Context Property — the everyday pattern

Python — backend/model.py 
from PySide6.QtCore import QObject, Signal, Slot, Property

class CounterBackend(QObject):
    countChanged = Signal(int)          # notify signal

    def __init__(self):
        super().__init__()
        self._count = 0

    @Property(int, notify=countChanged)
    def count(self):
        return self._count

    @Slot()
    def increment(self):
        self._count += 1
        self.countChanged.emit(self._count)
QML — consuming the context property 
import QtQuick
import QtQuick.Controls

ApplicationWindow {
    visible: true

    Text {
        // auto-updates whenever backend.countChanged is emitted
        text: "Count: " + backend.count
    }

    Button {
        text: "Increment"
        onClicked: backend.increment()   // calls the @Slot
    }
}

Registered Type — for QML-side instantiation

Use qmlRegisterType (or the @QmlElement decorator) when you need to create the object inside QML, e.g. for reusable models in component files.

Python — register the type 
from PySide6.QtQml import QmlElement

QML_IMPORT_NAME = "MyApp"
QML_IMPORT_MAJOR_VERSION = 1

@QmlElement
class CounterBackend(QObject):
    ...   # same class body as above
QML — instantiate inline 
import MyApp 1.0

CounterBackend { id: counter }
Text { text: counter.count }

4 Signals & Slots — The Communication API

Signals and slots are the core event bus. Understand the direction before you wire anything up.

DirectionMechanismWhen to use
Python → QML Signal declaration + .emit() Data ready, async operation complete, timer tick, model changed
QML → Python @Slot decorated method Button click, user input, request for action or data fetch
QML → QML Property bindings, QML signal + onSignal Within a component tree — parent/child communication

Defining signals with payload

Python — typed signals 
from PySide6.QtCore import QObject, Signal

class DataBackend(QObject):
    # Signal with no payload
    resetRequested = Signal()

    # Signal carrying typed data
    itemLoaded = Signal(str, int)     # (name: str, score: int)

    # Signal with a dict payload (use 'object' type)
    configUpdated = Signal(object)    # passes any Python object

Listening in QML with Connections

QML — Connections block 
Connections {
    target: backend                       // the Python QObject

    function onItemLoaded(name, score) {
        console.log("Got:", name, score)
        myLabel.text = name
    }

    function onResetRequested() {
        listView.model.clear()
    }
}

Slots — what Python exposes to QML

Python — @Slot rules 
from PySide6.QtCore import Slot

class Backend(QObject):

    # No args, no return value
    @Slot()
    def doWork(self): ...

    # Args must be declared as types
    @Slot(str, int)
    def addItem(self, name: str, score: int): ...

    # Return value annotated with 'result='
    @Slot(int, result=str)
    def getLabel(self, index: int) -> str:
        return self._data[index]
✅
Always declare argument types in @Slot.

Without type declarations PySide6 uses Python's dynamic dispatch, which can silently fail or pass the wrong type when called from JS (e.g. JS numbers become float instead of int).

5 Reactive Properties

A @Property with a notify signal is what enables QML's binding engine to react to Python-side value changes automatically. This is the primary way to share live state between layers.

Python — full property pattern 
from PySide6.QtCore import QObject, Signal, Property, Slot

class ViewModel(QObject):
    # Step 1: Declare the notify signal
    progressChanged = Signal(float)
    labelChanged    = Signal(str)

    def __init__(self):
        super().__init__()
        self._progress = 0.0
        self._label    = ""

    # Step 2: Getter decorated with @Property
    @Property(float, notify=progressChanged)
    def progress(self):
        return self._progress

    # Step 3: Setter emits the notify signal
    @progress.setter
    def progress(self, value: float):
        if self._progress != value:
            self._progress = value
            self.progressChanged.emit(value)  # QML re-evaluates all bindings

    @Property(str, notify=labelChanged)
    def label(self): return self._label
QML — binding to a Python property 
ProgressBar {
    // Re-evaluates automatically when vm.progressChanged fires
    value: vm.progress
}

Text {
    text: vm.label + " (" + Math.round(vm.progress * 100) + "%)"
}
⚠️
Guard emission with an equality check.

Emitting the notify signal when the value hasn't actually changed wastes binding evaluations and can cause subtle cycles. Always check if self._x != value before emitting.

6 UI/UX Design in QML

QML is a declarative UI language — describe what the UI looks like, not how to draw it step by step. Think in terms of a visual tree where every node is a rectangle with optional content, behaviours, and children.

Design-to-QML workflow

  1. Sketch the zones — Split the screen into 2–4 top-level zones (toolbar, sidebar, content, footer). Map each zone to a Qt Quick layout or SplitView.
  2. Choose a layout primitive — Prefer layouts (ColumnLayout, RowLayout, GridLayout) over raw anchors for dynamic resizing. Use SplitView for user-resizable panels.
  3. Pick the right controls — Use QtQuick.Controls 2 items (Button, TextField, ComboBox…) for interactive elements; use plain Item / Rectangle for purely visual shapes.
  4. Define a style token set — Declare colours, radii, font sizes, and spacing as readonly property values in a root-level QtObject and reference them everywhere.
  5. Add motion last — Wire up Behavior on, NumberAnimation, and Transition only after the static layout is correct.

Style token pattern

QML — centralised design tokens 
// Theme.qml — import everywhere as a singleton
pragma Singleton
import QtQuick

QtObject {
    readonly property color bg:        "#0d1117"
    readonly property color surface:   "#161b22"
    readonly property color accent:    "#58a6ff"
    readonly property color textMain:  "#e6edf3"
    readonly property color textMuted: "#8b949e"

    readonly property int   radius:    8
    readonly property int   spacing:   12
    readonly property int   fontSizeBody: 13
    readonly property int   fontSizeLabel: 11
}

Responsive sizing rules

  • Size windows in pixels; size internal elements with Layout.fillWidth / fillHeight, not fixed px.
  • Use implicitWidth / implicitHeight in custom components so parent layouts can make informed sizing decisions.
  • Prefer font.pixelSize over font.pointSize for consistent cross-DPI rendering on desktop.
  • Set minimumWidth and minimumHeight on the root Window to prevent the UI from collapsing.

Visual hierarchy checklist

ElementGuideline
Primary actionHigh-contrast fill button; one per panel maximum
Secondary actionOutlined or ghost button; lower visual weight
Destructive actionRed accent; separate from the normal action group
Empty statesAlways show a message/icon when a list is empty — never a blank rectangle
Loading statesUse BusyIndicator or a skeleton shimmer rather than blocking the UI
FeedbackEvery user action must produce visible feedback within 100 ms (animation, state change, or status text)

7 Layouts & Anchors

QML provides two positioning systems. Knowing which to reach for — and when not to mix them — prevents most layout headaches.

SystemUse when…Avoid when…
Anchors Positioning one item relative to another in free-form items (a floating badge, a close button pinned to a corner) Inside ColumnLayout / GridLayout children — mixing anchors and layout attached properties causes a warning and undefined behaviour
ColumnLayout / RowLayout A linear list of items that share available space, need gaps, or should wrap Single-item centering (use anchors.centerIn instead)
GridLayout Form-style label+field pairs, anything that needs row and column spanning Deeply irregular layouts — it becomes harder to read than nested rows/columns
SplitView User-resizable panels (IDE layout, file browser + editor) Fixed-proportion panels — use a regular RowLayout with explicit ratios
StackLayout Tab content, wizard pages — only one child visible at a time Animated page transitions — use StackView instead
✅ Do — Layout attached properties
ColumnLayout {
    spacing: 8
    Rectangle {
        Layout.fillWidth:  true
        Layout.fillHeight: true
    }
}
❌ Don't — Anchors inside Layout
ColumnLayout {
    Rectangle {
        // WARNING: cannot use anchors inside layout
        anchors.fill: parent
    }
}

8 Components & Reuse

Any QML block you copy more than once should become its own component file. A well-designed component is self-contained: it receives data through required property, fires actions through signal, and never reaches outside its own subtree.

Anatomy of a reusable component

QML — StatusChip.qml 
import QtQuick
import QtQuick.Controls

Rectangle {
    // ── Public API ─────────────────────────────────────
    required property string label
    required property color  chipColor
    property          bool   removable: false
    signal removed()                      // signal, not a function

    // ── Internal sizing ────────────────────────────────
    implicitWidth:  row.implicitWidth + 16
    implicitHeight: 26
    radius:         13
    color:          Qt.alpha(chipColor, 0.15)
    border.color:   Qt.alpha(chipColor, 0.4)

    Row {
        id: row
        anchors.centerIn: parent
        spacing: 4
        Label { text: label; color: chipColor; font.pixelSize: 11 }
        Label {
            visible: removable
            text: "×"
            color: chipColor
            MouseArea { anchors.fill: parent; onClicked: removed() }
        }
    }
}

required property vs property

KeywordMeaningWhen to use
required property Caller MUST provide this value. QML will warn if it's missing. Data a component cannot work without (e.g. delegate's model data)
property Optional — has a default value or can be left unset. Configuration options (spacing, editable, readOnly)
readonly property Computed or constant — cannot be written from outside. Derived values, constants, design tokens
💡
Delegates always use required property.

When a ListView or TableView instantiates a delegate, it injects model role values via required property. Never use the implicit model context object — required property is faster, type-safe, and works with TableView.

9 Models & Views

The Qt Model/View pattern cleanly separates data storage from presentation. Pick the right base class for your data shape.

Base classData shapeQML view
QAbstractListModelFlat list of homogeneous itemsListView, Repeater, ComboBox
QAbstractTableModel2-D grid (rows × columns) with headersTableView + HorizontalHeaderView
QAbstractItemModelHierarchical / tree structureTreeView
QSortFilterProxyModelWraps any model; adds filter + sortAny view (proxy is transparent)

Minimal QAbstractListModel

Python — minimal list model 
from PySide6.QtCore import (QAbstractListModel, QModelIndex,
                              Qt, Slot)

class TaskModel(QAbstractListModel):
    NameRole  = Qt.UserRole + 1
    DoneRole  = Qt.UserRole + 2

    def __init__(self):
        super().__init__()
        self._tasks = []                          # [{name, done}, ...]

    # ── Required overrides ─────────────────────────────
    def rowCount(self, parent=QModelIndex()):
        return 0 if parent.isValid() else len(self._tasks)

    def data(self, index, role=Qt.DisplayRole):
        if not index.isValid(): return None
        task = self._tasks[index.row()]
        if   role == self.NameRole: return task["name"]
        elif role == self.DoneRole: return task["done"]

    def roleNames(self):
        return {self.NameRole: b"name", self.DoneRole: b"done"}

    # ── CRUD ────────────────────────────────────────────
    @Slot(str)
    def addTask(self, name: str):
        row = len(self._tasks)
        self.beginInsertRows(QModelIndex(), row, row)
        self._tasks.append({"name": name, "done": False})
        self.endInsertRows()

    @Slot(int)
    def removeTask(self, row: int):
        self.beginRemoveRows(QModelIndex(), row, row)
        self._tasks.pop(row)
        self.endRemoveRows()
🚫
Never mutate _data without begin/end pairs.

Always bracket insertions with beginInsertRows / endInsertRows and deletions with beginRemoveRows / endRemoveRows. Skipping these causes the view to show stale data or crash.

Connecting model to a ListView

QML — ListView with required property delegate 
ListView {
    model: taskModel                  // context property from Python
    delegate: ItemDelegate {
        // Inject model roles via required property
        required property string name
        required property bool   done

        text: name
        opacity: done ? 0.4 : 1.0
    }
}

10 States & Transitions

QML's states + transitions system is the right tool for elements that have distinct visual modes (normal, hovered, pressed, expanded, error). Keep state logic in QML; keep business logic in Python.

QML — state machine for a card 
Rectangle {
    id: card
    color: "#161b22"
    border.color: "#30363d"
    scale: 1.0

    states: [
        State {
            name: "hovered"
            when: mouseArea.containsMouse
            PropertyChanges { target: card; border.color: "#58a6ff" }
        },
        State {
            name: "pressed"
            when: mouseArea.pressed
            PropertyChanges { target: card; scale: 0.97 }
        }
    ]

    transitions: [
        Transition {
            ColorAnimation  { duration: 150 }
            NumberAnimation { property: "scale"; duration: 100; easing.type: Easing.OutQuad }
        }
    ]

    MouseArea { id: mouseArea; anchors.fill: parent; hoverEnabled: true }
}

Behavior on vs Transition

ToolBest for
Behavior on xAny time a single property changes, regardless of cause — springs, smooth follow
TransitionCoordinated multi-property animations triggered by an explicit state change
NumberAnimation standaloneFire-and-forget animations driven imperatively (e.g. Play button)
SequentialAnimationChain multiple animations with delays and pauses in order

11 Backend Model Reference

Quick decision guide for choosing the right Python model base class.

QAbstractListModel — flat lists

Override: rowCount(), data(), roleNames(). For mutable lists also implement setData() and flags().

QAbstractTableModel — 2-D grids

Add columnCount() and headerData() on top of the list overrides. Bracket all mutations with beginInsertRows/endInsertRows, beginInsertColumns/endInsertColumns, beginRemoveRows/endRemoveRows.

QAbstractItemModel — trees

The hardest base class. The index()/parent() contract must be self-consistent:

  • index(row, col, parent) → returns a QModelIndex whose internalPointer is the child node object.
  • parent(child_index) → returns the index for the child's parent node, using the grandparent as the new parent argument.
  • For a root-level item, parent() must return an invalid QModelIndex().

QSortFilterProxyModel — filter + sort overlay

Python — proxy model pattern 
from PySide6.QtCore import QSortFilterProxyModel, Qt, Slot

class FilterProxy(QSortFilterProxyModel):
    def __init__(self, source_model):
        super().__init__()
        self.setSourceModel(source_model)
        self._search = ""

    @Slot(str)
    def setSearch(self, text: str):
        self._search = text.lower()
        self.invalidateFilter()             # re-evaluate all rows

    def filterAcceptsRow(self, source_row, source_parent):
        idx   = self.sourceModel().index(source_row, 0, source_parent)
        name  = self.sourceModel().data(idx, Qt.DisplayRole) or ""
        return self._search in name.lower()

    # Expose proxy to QML as a context property (not the source)
    # engine.rootContext().setContextProperty("model", proxy)
✅
Use mapToSource() when deleting through the proxy.

Calling source_model.removeRow(proxy_row) deletes the wrong row. Always call proxy.mapToSource(proxy.index(proxy_row, 0)).row() to get the true source row first.

12 Threading & Real-time Data

All QML / Qt operations must happen on the main thread. Long-running Python tasks must run in a worker and communicate back via signals — never touch the model or UI from a background thread.

Safe pattern: QThread worker

Python — worker thread pattern 
from PySide6.QtCore import QObject, QThread, Signal, Slot

class Worker(QObject):
    resultReady = Signal(object)          # emits result to main thread
    finished    = Signal()

    @Slot()
    def run(self):
        data = slow_computation()           # runs in worker thread
        self.resultReady.emit(data)         # safe — Qt queued connection
        self.finished.emit()

class Controller(QObject):
    def start(self):
        self._thread = QThread()
        self._worker = Worker()
        self._worker.moveToThread(self._thread)

        self._thread.started.connect(self._worker.run)
        self._worker.finished.connect(self._thread.quit)
        self._worker.resultReady.connect(self._on_result)  # main thread

        self._thread.start()

    def _on_result(self, data):
        # This slot runs on the main thread — safe to update model
        self._model.appendData(data)

QTimer for periodic live data

For periodic UI updates (live charts, dashboards) prefer QTimer on the main thread over a background thread — it's simpler and inherently thread-safe.

Python — QTimer live data 
from PySide6.QtCore import QObject, QTimer, Signal
import random, math

class LiveBackend(QObject):
    newPoint = Signal(float, float)   # (x, y)

    def __init__(self):
        super().__init__()
        self._t = 0.0
        self._timer = QTimer(self)
        self._timer.timeout.connect(self._tick)

    @Slot()
    def start(self): self._timer.start(200)   # 200 ms

    @Slot()
    def stop(self):  self._timer.stop()

    def _tick(self):
        y = math.sin(self._t) + random.uniform(-0.1, 0.1)
        self.newPoint.emit(self._t, y)
        self._t += 0.2

13 Common Pitfalls & Fixes

1 · Binding loops

A binding loop occurs when property A depends on B and B depends on A. QML detects them and prints a warning; the binding eventually breaks.

✅ Break the loop with Qt.callLater
onEditingFinished: {
    // Defer the update until after the
    // current binding evaluation is done
    Qt.callLater(function() {
        myField.text = backend.value
    })
}
❌ Direct circular binding
// text ← backend.value → text loops
TextField {
    text: backend.value
    onTextChanged: backend.setValue(text)
}

2 · Accessing destroyed delegates

If a ListModel.remove() is called inside a signal handler fired from a delegate, that delegate may be destroyed before the handler finishes. Any QML id lookup will throw ReferenceError.

QML — capture ids before triggering destruction 
MouseArea {
    onClicked: {
        // Capture BEFORE the drop, which may destroy this delegate
        var rootRef  = root
        var proxyRef = root.proxy
        proxyRef.Drag.drop()        // may destroy delegate's QML context
        proxyRef.visible = false
        rootRef.dragSourceCol = -1
    }
}

3 · color property in ListModel

A property color foo stores a QColor object. Appending it to a ListModel role that was seeded as a string crashes with a type mismatch.

✅ Store as string
property string accentColor: "#58a6ff"
// Pass the string into ListModel safely
❌ Store as color object
property color accentColor: "#58a6ff"
// TypeError when appended to ListModel

4 · Canvas font strings

When drawing text on a QML Canvas, multi-word font families must be quoted: "11px 'Segoe UI'". Without the inner quotes Qt prints an "invalid font families" warning and falls back to the default font.

5 · Slot type mismatch from JS

JavaScript passes all numbers as float. Declare @Slot(int) or @Slot(float) explicitly so PySide6 coerces the type correctly. An untyped @Slot receives a Python float even when you pass an integer literal from QML.

6 · Object ownership and garbage collection

Python objects passed to QML become owned by QML's garbage collector unless you set QQmlEngine.setObjectOwnership(obj, QQmlEngine.CppOwnership). For context properties this is set automatically, but for objects returned from @Slot you must manage ownership explicitly.

14 Developer Checklist

Run through this list before shipping any PySide6 + QML feature.

Architecture

  • ☐ Backend classes inherit QObject and contain zero UI logic
  • ☐ Entry point creates all backends before loading QML
  • ☐ Context properties are registered with meaningful, stable names
  • ☐ QML never imports Python modules or calls os / sys directly

Signals & Slots

  • ☐ Every @Slot has explicit argument type declarations
  • ☐ Every @Property has a matching notify signal
  • ☐ Notify signals are only emitted when the value actually changes
  • ☐ No Python logic executes directly in a QML binding expression

Models

  • ☐ All insertions/deletions are wrapped in begin/end pairs
  • ☐ Delegates use required property instead of implicit context
  • ☐ Proxy deletions go through mapToSource()
  • ☐ resetTable / batch changes use beginResetModel / endResetModel

UI / QML

  • ☐ Layout children don't mix anchors with Layout.* attached properties
  • ☐ Components expose a typed public API (required property + signal)
  • ☐ No QML component reaches for a global context property it wasn't given
  • ☐ Every interactive element provides visible hover / pressed feedback
  • ☐ Canvas font strings use quoted families: "14px 'Segoe UI'"

Threading

  • ☐ Model mutations only happen on the main thread
  • ☐ Worker threads communicate via signals (queued connection), not direct calls
  • ☐ QTimer is used for periodic UI updates instead of time.sleep
🚀
Start simple, add complexity incrementally.

Resist the urge to build the complete architecture upfront. Start with a single QObject context property and a flat QML file. Extract components and model base classes only when the pain of duplication becomes real.
